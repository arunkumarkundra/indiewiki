## Define the outcome before the feature list

Describe the user, their starting situation, and the result they need. “Create a dashboard” is a feature; “know which invoices need attention before Friday” is an outcome. Identify the smallest workflow that can deliver that result with acceptable effort and trust.

List the assumptions the workflow depends on: data access, user skill, timing, accuracy, and willingness to change habits. Some steps may be done manually behind the scenes while you learn. Be honest with users about what is automated and what is not.

## Cut scope without breaking the promise

For each proposed feature, ask whether the user can complete the core task without it. Defer secondary roles, advanced customization, speculative integrations, and scale work that has no current evidence behind it. Keep security, privacy, accessibility, and recovery needs in scope when they protect the core outcome.

A narrow MVP is not permission to ship a misleading or unsafe experience. Set boundaries for data handling, failure states, and support before inviting real users.

## Learn from use

Define one activation event that represents meaningful progress, then observe where users get stuck. Combine quantitative product events with conversation and support context. Small early samples are diagnostic, not statistically representative. Update the roadmap when observed needs contradict your initial assumptions.
